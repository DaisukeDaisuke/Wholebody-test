# 実画像評価の範囲

GitHub Actionsの`Actual-image pose evaluation`で公開画像を実際にONNXへ入力し、正解注釈との2D位置誤差を測る。ローカルやクラウドブラウザの手動テストは行わない。

初期セットはCOCO-WholeBody作者が公開した`evaluation/example_gt.json`と、対応する4枚のCOCO検証画像である。画像IDは785、40083、196141、197388。人物ID順で最大12人を選ぶ。小規模な実画像比較であり、論文の全検証セットAPや実利用一般の精度とは異なる。`workflow_dispatch`の`dataset=val-subset`と`people`で正式検証注釈から対象を増やせる。`val-subset`では初期4画像を除外し、人物IDのSHA-256順でサンプルを固定する。モデルの学習や閾値調整には使用しない。

通常のpushで64人評価を再実行するのは、モデル定義・推論処理・画像評価スクリプト・評価workflowが変わったときだけである。一般のUI・LAN変更は`Application syntax`で構文を確認する。画像評価では追加でRTMDetの実画像1枚を推論し、出荷経路のBGR正規化入力で人物BBoxのIoUが0.5以上になることを確認する。この1枚は一般的な人物検出率の証明ではない。

現在のpush・手動実行の既定モデルは、新候補の`rtmw-l-384`（入力384×288）だけである。完了済みのS/L基準値を同じ変更で何度も再計測しない。過去の比較は手動実行で`models=rtmpose-s,rtmw-l`を指定すれば再現できる。新候補も同一の固定64人・同じ注釈・同じ評価定義で測定し、元モデルの基準値と比較する。

## 比較

RTMPose-S FP32、RTMW-L FP32の全身推論を同じ人物ROIで比較する。さらにOpenCV ZooのMediaPipe手専用ONNXを追加し、同じ画像の手位置が改善するか悪化するかを測る。手の回転ROIは全身モデルの予測した掌7点だけから作る。正解の手位置・手BBoxは手推論へ入力しない。正解の人物BBoxは利用するため、人物検出器の性能はこの評価に含まれない。

元画像と、手または足を灰色矩形で隠した画像を比較する。矩形実験は既知の正解を保持した静止画の入力劣化実験であり、現実の布・人体による遮蔽や時系列追跡の精度とは別の結果として扱う。

## 指標

Body、feet、handsを別々に集計し、平均・中央値・p95画素誤差、人物BBox長辺の5%と10%を閾値とするPCK、手BBox長辺の20%を閾値とするHand PCKを出す。正解注釈が有効であれば、モデルが低信頼でも位置誤差の分母から外さない。信頼度0.25以上の被覆率も独立表示する。Bodyのみ、公式の可視`v=2`と遮蔽`v=1`を分ける。手足の`v`には小数の信頼値が認められているため、整数1/2を遮蔽の定義として流用しない。

モデルURL、revision、SHA-256、実ONNX入力・出力名とshape、選択した人物ID、画像SHA-256、推論バックエンドを`report.json`へ保存する。予測値JSONと、正解・全身モデル・手refinementを重ねた証拠画像も保存する。モデルの巨大なバイナリをActions成果物へ再アップロードしない。

公開用overlayはCOCOのlicense ID 4（CC BY 2.0）の画像に限定し、固定選択順の先頭6人までを保存する。数値評価の64人は変更せず、画像の公開可否で誤差の集計対象を変えない。原画像URL、Flickr URL、ライセンスIDを同じreportに保持する。初期のartifactにはこの絞込み以前の画像が含まれるため、サイトへ転載する証拠画像は別途この条件で選ぶ。

## 3Dと実機の境界

`verify-geometry.mjs`は、異なるカメラ中心・校正・時刻を使った三角測量の数学契約と、予測の失効を検査する。これは既知の合成3D入力による実装検証であり、実カメラでのセンチメートル精度の証拠ではない。実機の2視点動画、本人骨長、撮影位置の正解、LAN端末間通信、RTXのWebGPU速度は、それぞれの実入力があるときに評価する。

`--panoptic-input`を指定した場合は、CMU Panopticの実画像推論から得た2視点観測と既知カメラ校正を、アプリと同じ`dist/geometry.js`の`triangulateJoint`と`dist/tracking.js`の`OcclusionTracker`へ入力する。正解3D座標は評価にだけ使用し、公開レポートには残さない。身体17点と左右の手42点について、利用可能な推定のMPJPE、推定が存在する割合、20/50/100mm以内のPCKを測る。PCKの分母は欠測を含む全有効正解点とし、難しい点を失効させただけで精度が良く見える集計を避ける。

中央8フレームで両手の全視点観測を除去する実験は、画像モデルの遮蔽性能とは分ける。これは実動作の3D正解に対し、時系列補完が観測欠測中にどこまで追従できるかを測る。元の観測・観測除去の両方について、直接三角測量と時系列追跡、全フレームと欠測区間の指標を個別に出す。

### 手presenceを観測遮断に使う案の検討

既存の推論結果だけを集計し、`presence <= 0.10`を候補に調べた。推論ROIを作れず手モデルを実行していない場合は、presenceゼロとして扱わず別に数えた。

| 全身モデル | 元画像の有効注釈手で低presence / presence取得手 | maskが触れた手で低presence / presence取得手 | ROI未実行（元画像 / mask対象） |
|---|---:|---:|---:|
| RTMPose-S | 10 / 44 | 23 / 27 | 1 / 45、5 / 32 |
| RTMW-L | 11 / 45 | 26 / 31 | 0 / 45、1 / 32 |

maskに対する反応はあるが、Lでも元画像の有効注釈手の24.4%を低presenceとした。例えば人物注釈1751582の左手はpresence 0.0208でも平均位置誤差1.28px、456968の右手は0.0838でも2.08pxだった。低presenceの11手を一律欠測へ変えると、元画像の全945手点を分母に保った人物PCK(.05)は85.40%から67.83%へ低下する。これは元の正しい166点まで失うためである。presenceを既定の可視性ゲートにせず、手ROIの採否にだけ使用する。時間履歴でこの損失を補えるかは、別の実系列評価が必要である。

ここで「元画像の有効注釈手」は自然遮蔽の厳密な可視ラベルではない。また、単に低presence点を指標の分母から外して改善したようには集計していない。

[Actions run 41378383899](https://github.com/DaisukeDaisuke/Wholebody-test/actions/runs/41378383899)は、コミット`e9bc84483c88884c7b88ed9589eb069a6070a903`で新候補64人、人物検出1画像、幾何契約が全て成功した。新候補の入力metadataは動的batchだが、実際の入力はbatch 1とし、実出力133点のshapeを検査している。旧256入力のartifactと人物IDの順序、注釈SHA-256、全64画像のSHA-256が一致しており、評価母集団を変えた比較ではない。

| RTMW-L構成 | 身体PCK(.05) | 足PCK(.05) | 手の中央値px | 手の平均px | Hand PCK(.20) |
|---|---:|---:|---:|---:|---:|
| 256×192、手ROIなし | 83.05% | 82.88% | 3.392 | 13.208 | 74.92% |
| 384×288、手ROIなし | 85.65% | 84.68% | 2.869 | 13.432 | 77.78% |
| 384×288、手ROIあり | 85.65% | 84.68% | 3.960 | 14.837 | 73.65% |

384入力は身体・足のPCKと手の中央値・PCKを改善した。一方、手の平均誤差は改善せず、p95誤差は256入力の57.56pxから79.33pxへ増えた。全指標で優位ではないため、外れ値と処理負荷も含めて選ぶ。384への手ROI追加は再び悪化しており、手ROIの既定OFFを維持する根拠となる。身体の自然遮蔽74点ではPCK(.05)64.86%。灰色maskをかけた同一633手点のHand PCK(.20)は原画像79.78%から18.64%へ下がり、mask後もスコア0.25以上の割合は100%だった。

最終のアプリ既定はRTMW-L 384×288・手ROI OFFとし、身体PCKと手のPCK・中央値の改善を優先した。256×192も処理負荷を抑える選択肢として残す。選択画面と公開数値では平均誤差・足・処理量の不利な点も併記する。

384の全身推論CPU平均は258.85msだった。256の149.93msとは別runnerの測定なので増加量は参考値であり、GPUや実端末の速度を表さない。これらは全身推論部分だけの時間で、画像転送・人物検出・手ROIなどを含むアプリ全体の遅延ではない。

成果物はartifact `13112480273`（ZIP SHA-256 `1ca2577fc78e14b3e616e3150dc68d394af9ac121febc591f2af8e6f251af031`）。`report.json`、`detector.json`、実推論座標、CC BY画像のみの6枚のoverlayを保存した。同じ入力の任意の再計測は行わない。

## 実系列評価の追加経路

`Hand multiview and recorded motion evidence`は、手21点の多視点評価と実運動の身体欠測補完の2種類に対象を絞る。公開HanCo Testerについては、固定したZIPの到達性、カメラ校正、手動検証済み参照frameをまずActionsで確認する。参照はMANO fitであり、独立光学モーションキャプチャ正解と同一視しない。画像cropにより変わる内部行列はframeごとのカメラ定義を使用する。

FreeMoCap validationは公開済みのRTMPose 3D系列と独立Qualisys marker参照を使用する。主要身体12点（肩・肘・手首・股・膝・足首）を対応させ、配布単位mmからmへ固定換算する。取得側は公開SHA256SUMSを照合し、body軸の固定回転以外に評価結果を良くする位置・尺度合わせをしない。配布元では既に系列の同期、剛体整列、補間、filter処理をしているため、カメラから出力までの因果精度の測定ではない。

評価入力は2条件に分ける。`rtmpose-to-qualisys`は記録済みRTMPose系列をアプリの因果trackerへ与え、Qualisysを参照する。`qualisys-to-qualisys`は参照系列自体を入力として、観測が失われた間の補完だけを分離する。1人・5速度条件を各300連続frameに固定し、中央8frameの両肘と両手首の観測を削除する。原観測・観測除去それぞれについて身体12点全体と対象腕4点、全frameと欠測区間を別集計する。これを手指や足の指の評価とは呼ばない。

両経路とも、`verify-geometry.mjs`がアプリと同じtrackerを使用し、平均3D誤差に加えて被覆率と全有効参照点を分母とする20/50/100mm PCKを出す。元の参照座標・配布Parquet・元画像は作業cacheに置き、公開artifactには集計と出典を保存する。Actionsで結果が得られるまでは、この経路の実精度が確認済みとは記載しない。

比較には、欠測を出力するraw経路と製品trackerに加え、直前に受け入れた観測座標を保持する`hold-last`を含める。これは正解座標を使わず、手250ms・足450ms・身体600msという製品の自由予測寿命で失効する。全区間と指定した欠測区間の誤差・PCK・被覆率を並べ、製品の補完が単純な位置保持を上回るかを確認する。製品の親関節へ固定した補完は別の寿命を持つため、被覆率の差も残して示す。

### HanCoの既存推論を使う固定2視点診断

既に成功した実画像推論の再計算はせず、`HanCo fixed-pair selection from recorded inference`がrun `41378383880`の観測artifactを読み直して幾何だけを評価する。元のcam0/3、元の8視点、片視点画像maskの4条件を残す。追加条件は、先頭10frameの予測スコアと既知カメラ幾何だけで8候補から固定2視点を選ぶ。28組を全て試し、アプリの三角測量confidenceの和を10×21点で割った値が最大の組を採る。同点はカメラID辞書順とし、3D参照や誤差を選択に使わない。

選んだ組は残りの系列で固定する。先頭10frameは履歴の初期化に使うが、追加条件の採点からは除外し、同じ採点区間の8視点条件も出す。各組のbaseline、再構成できた点数、平均ray角、平均再投影誤差、拒否理由を保存するため、元のcam0/3が失敗する理由も確認できる。この選択に新しいモデル、参照母集団、画像推論は追加しない。

fresh画像推論とFreeMoCap、固定2視点診断のworkflowは、必要な実測を完了後は手動実行として保持する。再利用元artifactの保持期間は7日なので、期限後はfresh workflowで元の観測を再生成し、再利用workflowの`source_run`と`source_artifact`にそのrunを指定する。

GTを見ないwarmup選択はcam3/4を選んだ。2台間距離は0.8001m、warmupの210関節時刻中200で再構成が成立し、平均ray角63.91度、平均再投影誤差2.211pxだった。以下は同じ63参照点に対する製品trackerの結果である。
